# Algorithm and technical-workflow inventions

Read this reference for algorithms, software, AI, data processing, optimization, control logic, or a workflow proposed as an invention.

## Technicality analysis

Do not reject or accept a proposal merely because it contains an algorithm, software, AI, or workflow. Examine the claim as a whole and identify the concrete technical problem, technical means, technical object or process, and causally linked technical effect.

A technically meaningful disclosure normally identifies:

- the origin and technical meaning of input data or signals;
- data structures, state variables, features, parameters, or models that participate in processing;
- the ordered transformation, calculation, decision, control, or update relationship;
- a computer, device, network, production process, measurement process, or other technical environment where that relationship operates;
- a technical output, device action, state change, resource behavior, or domain result;
- the mechanism connecting the operations to the asserted effect.

Do not add nominal hardware merely to decorate an otherwise non-technical rule. Conversely, do not assume that a technical method must claim a particular processor model or physical component when the disclosed interaction is already concrete.

## Algorithm disclosure checklist

Disclose what is needed to reproduce the algorithmic mechanism, as applicable:

- input schema, source, sampling or acquisition, units, encoding, coordinate or reference conventions, and validity conditions;
- preprocessing, normalization, segmentation, synchronization, filtering, feature construction, and missing-data behavior;
- equations, objective functions, constraints, update rules, thresholds, model structure, pseudocode, or deterministic decision logic;
- training and inference distinction when learning is involved;
- how training data, labels, losses, validation, stopping, deployment, and model updates affect the claimed mechanism when material;
- initialization, iteration, convergence or termination, exception handling, and fallback;
- output schema and how downstream software, equipment, or a technical process consumes the result;
- computational, communication, storage, control, accuracy, robustness, or physical effect, together with a credible verification method;
- alternative algorithms and narrower fallback implementations that preserve the inventive relationship.

“Using a neural network”, “performing optimization”, “intelligently deciding”, or “automatically processing” is not an implementation path.

## Workflow disclosure checklist

Convert a workflow into explicit technical state and control relationships:

- participating technical modules or controlled objects;
- start state, trigger, prerequisites, and input ownership;
- message, data, material, energy, or control transfer between stages;
- state transitions and the conditions that cause them;
- branches, loops, retries, timeouts, conflict resolution, and rollback;
- synchronization, ordering, concurrency, idempotence, and version behavior when material;
- end state, output, and downstream technical action;
- how the workflow changes technical operation rather than only assigning human, business, or administrative responsibility.

If the only effect is pricing, advertising, contractual allocation, management convenience, presentation of information, or a mental decision, flag the technical-subject-matter risk instead of inventing a technical effect.

## Artificial intelligence and data constraints

For a model-building or training contribution, disclose the modules, levels or connection relationships, training steps, necessary parameters, and the technical role of those features to the extent needed by the claimed contribution. For application of a model in a specific field, disclose the input and output settings and their intrinsic relationship to the technical scenario.

Do not invent datasets, labels, consent, legality, model parameters, training results, or bias testing. Flag a blocking issue when the claimed mechanism materially depends on unlawful data acquisition, prohibited use, fabricated provenance, or a result contrary to law or public interest.

## From idea to claim

Build the independent claim around the smallest complete causal chain. A useful internal pattern is:

1. obtain a technically defined input or state;
2. construct or update a defined intermediate representation;
3. apply specified relationships, constraints, or decision conditions;
4. generate a defined technical result or control action;
5. use or validate that result in the technical context when that interaction is part of the inventive mechanism.

This is a reasoning pattern, not mandatory claim wording. Omit steps that are not indispensable, and do not add a generic “processor executes instructions” limitation without a scope reason.

## Effects and quantitative statements

Map each asserted effect through a causal chain:

`distinguishing feature → changed data/device/computation/physical relationship → technical consequence → evidence maturity`.

Quantitative superiority requires traceable tests, datasets, logs, simulations, or calculations. Without that support, use qualitative mechanism-based language and identify the proposed verification method.

Simulation results must remain labeled as simulations. Hypothetical examples must use conditional or embodiment language and must not be described as measured facts.
